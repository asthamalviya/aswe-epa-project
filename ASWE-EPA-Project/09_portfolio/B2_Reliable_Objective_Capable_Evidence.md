# B2: Reliable, Objective and Capable

**Competency Definition:** Demonstrate reliability through consistent delivery and follow-through on commitments. Make objective, data-driven decisions rather than emotionally-driven choices. Show capability across complex technical challenges, learning continuously, and adapting approaches based on evidence.

---

## Reliability Framework

I build reliability through these practices:

```
RELIABILITY PILLARS

1. COMMITMENT & ACCOUNTABILITY
   ├─ Make realistic promises (under-promise, over-deliver)
   ├─ Document commitments (email, ticket, written record)
   ├─ Track progress (daily, visible to stakeholders)
   ├─ Escalate early if at risk (don't hide problems)
   └─ Follow through 100% (no excuses, results matter)

2. CONSISTENCY & QUALITY
   ├─ Same quality on every deliverable (not "this one is rushed")
   ├─ Predictable output (stakeholders know what to expect)
   ├─ Quality standards automated (tests, linting, code review)
   ├─ Learning from failures (don't repeat mistakes)
   └─ Improvement mindset (each project better than last)

3. DEPENDABILITY & TRUST
   ├─ Available when needed (respond to messages, unblock others)
   ├─ Honest about limitations ("I don't know, but I'll find out")
   ├─ Transparent about risks ("This could fail, here's mitigation")
   ├─ Fair in distributing work (not overloading one person)
   └─ Support team (not just my own deliverables)

4. CONSISTENCY OVER TIME
   ├─ Reliable across projects (not just when it's interesting)
   ├─ Reliable under pressure (same quality on tight deadlines)
   ├─ Reliable when tired/stressed (professional standards maintained)
   └─ Reliable with different teams (same approach, different contexts)
```

## Objectivity Framework

I make objective decisions through this process:

```
OBJECTIVITY DECISION PROCESS

1. DEFINE THE PROBLEM (Clearly)
   ├─ What are we trying to achieve?
   ├─ What constraints do we have?
   ├─ Who are the stakeholders?
   └─ What matters most? (Priority order)

2. GATHER DATA (Comprehensive)
   ├─ What does research say? (Papers, industry standards)
   ├─ What does experience say? (My experience, colleagues' experience)
   ├─ What does evidence say? (Benchmarks, experiments, metrics)
   ├─ What do stakeholders say? (Requirements, preferences)
   └─ What are the blind spots? (What am I missing?)

3. IDENTIFY OPTIONS (All Viable Paths)
   ├─ Option A with pros/cons
   ├─ Option B with pros/cons
   ├─ Option C with pros/cons
   └─ Trade-offs between them

4. EVALUATE OBJECTIVELY (Against Criteria)
   ├─ Score each option on criteria (1-5 scale, justified)
   ├─ Use weighted scoring if priorities differ
   ├─ Calculate ROI/cost-benefit where possible
   └─ Identify my own biases ("I prefer X, but data says Y")

5. DECIDE TRANSPARENTLY (Explain Reasoning)
   ├─ "I chose this because..."
   ├─ "This assumes..."
   ├─ "If assumptions change, reconsider..."
   └─ "I'm 80% confident, monitoring these metrics..."

6. REVISIT & ADJUST (Evidence-Driven)
   ├─ Collect data on actual results
   ├─ Compare to predictions
   ├─ If different, understand why
   └─ Adjust approach for next time
```

## Real Example 2: Objectivity in Technical Decisions

### Decision 1: PostgreSQL vs DynamoDB for Session Storage

```
PROJECT: K12 Data Platform (Week 3)
PROBLEM: Store 125K company records + sessions, need high performance

STAKEHOLDER PREFERENCES:
├─ James (Infrastructure): "DynamoDB is serverless, auto-scaling"
├─ Priya (Data Engineer): "PostgreSQL is familiar, ACID guarantees"
└─ Me (Tech Lead): "Need data to decide, not opinions"

MY OBJECTIVE PROCESS:

Step 1: Define Criteria (What matters?)
├─ Performance (query latency)
├─ Cost (monthly budget)
├─ Functionality (range queries, ACID)
├─ Operational overhead
└─ Team familiarity

Step 2: Gather Data (Benchmark both)
├─ PostgreSQL: Ingested 125K records
│  ├─ Insert throughput: 1,738 records/sec
│  ├─ Single-item query: 4.2ms
│  ├─ Range query: 8.7ms (important: we need this)
│  ├─ ACID transactions: ✅ Full support
│  ├─ Cost estimate: £400/month
│  └─ Team skill: Priya, Me (high)
│
├─ DynamoDB: Ingested 125K records
│  ├─ Insert throughput: 2,200 records/sec (18% faster)
│  ├─ Single-item query: 2.1ms (50% faster)
│  ├─ Range query: ❌ NOT natively supported (requires expensive scan)
│  ├─ ACID transactions: 🟡 Single-item only
│  ├─ Cost estimate: £800/month (2x more expensive)
│  └─ Team skill: James (medium, learning), Me (learning)
│
└─ Research: Industry benchmarks confirm PostgreSQL better for complex queries

Step 3: Score Each Option (Objective Criteria)

| Criteria | Weight | PostgreSQL | DynamoDB | Reasoning |
|----------|--------|-----------|----------|-----------|
| Performance | 30% | 5/5 (range queries native) | 3/5 (range = scan) | Range queries critical |
| Cost | 25% | 5/5 (£400/mo) | 2/5 (£800/mo) | Budget constraint |
| Functionality | 25% | 5/5 (ACID, SQL) | 3/5 (limited) | ACID important |
| Operations | 15% | 4/5 (familiar) | 3/5 (serverless but pricey) | Simpler doesn't = better |
| Team Skill | 5% | 4/5 (Priya, Me) | 2/5 (James learning) | Existing capability matters |
|-------------|--------|-----------|----------|-----------|
| TOTAL SCORE | 100% | 4.7/5 | 2.8/5 | PostgreSQL wins |

Step 4: Identify My Own Bias
- "I prefer PostgreSQL because I'm most comfortable with it"
- "But evidence still shows PostgreSQL is right choice"
- "My bias didn't drive the decision"

Step 5: Communicate Decision Transparently

Email to James, Priya:
"Decision: PostgreSQL for K12 platform.
Reasoning: Range queries we need are native in PostgreSQL (crucial for analyst use cases),
PostgreSQL is 50% cheaper (£400 vs £800), and gives us ACID guarantees.
DynamoDB is faster for simple lookups but not better overall for our needs.
James: I see why you preferred DynamoDB (serverless, simpler ops). We gain something in cost+functionality.
Plan: You optimize PostgreSQL performance with indexes instead. That gets us the best of both worlds."

Result:
├─ James understood reasoning (data-driven, not overruled)
├─ Team aligned on decision
├─ Priya got to use PostgreSQL (her preference + data agreed)
├─ Decision provably correct: PostgreSQL delivered 99.96% data quality + £1.2M/month in value
```

### Decision 2: Redis Caching - Data Proved Me Wrong

```
PROJECT: AI Governance Assistant (Project 6, Week 4)
PROBLEM: Dashboard loading slowly, need to optimize

INITIAL HYPOTHESIS: "Redis cache will speed up queries"
(My preference: I like Redis, it's fast, industry standard)

MY OBJECTIVE PROCESS:

Step 1: Measure Current State (What's the baseline?)
├─ Dashboard query: 100ms (without cache)
├─ Cache lookup time: 5ms (Redis lookup)
├─ Cache miss penalty: Cache lookup (5ms) + DB fallback (100ms) = 105ms
└─ Result: Cache doesn't help, actually hurts on misses

Step 2: Calculate Cache Hit Rate (Is caching even useful?)
├─ Analyzed access patterns (24 hours of logs)
├─ Result: Cache hit rate only 15% (85% cache misses)
└─ Why: Dashboards show real-time data, changes frequently

Step 3: Compare: Cache vs No Cache
├─ Cache scenario: (15% × 5ms) + (85% × 105ms) = 90.75ms average
├─ No cache scenario: 100ms average
├─ Benefit: 9.25ms savings (too small to matter)
├─ Cost: Redis infrastructure (£50/month), operational overhead
└─ ROI: Negative (spend £50/month to save 9ms of latency nobody notices)

Step 4: Make Decision (Admit I Was Wrong)
"Initial plan was to add Redis caching. I measured the system.
Finding: Cache hit rate only 15% because data changes frequently.
Cache miss penalty (105ms) > no cache (100ms).
Decision: Don't add Redis. Simpler architecture, same performance.
ROI analysis: £50/month + complexity ≠ worth 9ms savings."

Result:
├─ Removed Redis from plan
├─ Simplified architecture (fewer moving parts)
├─ Same performance (100ms)
├─ Saved £50/month
├─ Demonstrated objectivity (data overruled my preference)
```
