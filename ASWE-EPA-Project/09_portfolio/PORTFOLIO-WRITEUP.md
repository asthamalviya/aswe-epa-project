**Mapped to:** Project 6 - AI Governance Assistant (Multi-tier system design)

**Definitional Understanding:** Systems architecture encompasses **multi-tier design**, **microservices patterns**, **scalability considerations**, **resilience & high availability**, and **technology trade-offs**.

**System Architecture: Multi-Tier Design**

```
User Devices (React) 
    ↓ HTTPS
CloudFront CDN (Global caching, DDoS protection)
    ↓ HTTPS
ALB (Load balancing, health checks, auto-scaling)
    ↓ HTTP (Private VPC)
Microservices (4 services: Governance, Document, User, Policy)
    ↓ SQL
PostgreSQL RDS (Multi-AZ, 99.99% uptime)
    ↓ Replication
S3 Medallion + Athena (Analytics, cost-efficient)
```

**Why Multi-Tier?**
- Separation of concerns (each layer has single responsibility)
- Independent scaling (heavy layer scales without others)
- Resilience (one layer fails, others keep working)
- Security (private subnets for sensitive data)

**Microservices Design:**
- 4 independent services (Governance, Document, User, Policy)
- Each scales independently (Governance high-traffic → scale it)
- Each deploys independently (update User service without others)
- Resilience patterns: Circuit breaker, retry with backoff, timeout, fallback

**Trade-offs (Microservices):**
| Aspect | Monolith | Microservices |
|--------|----------|---|
| **Scaling** | Entire app | By service (efficient) |
| **Deployment** | Entire app redeploy | One service (fast) |
| **Complexity** | Simple architecture | Distributed systems (hard) |
| **Result** | **Simpler, slower to iterate** | **Complex, fast to scale** |

---

**Architectural Decision Records (ADRs):**

1. **Microservices vs Monolith:** Chose microservices for independent scaling/deployment
2. **SQL + Redis vs NoSQL:** Chose both (consistency via SQL, speed via cache)
3. **Auto-scaling vs Fixed:** Chose auto-scaling (min 2, max 10 instances) → 80% cost savings
4. **Multi-AZ vs Single AZ:** Chose Multi-AZ (£2,400/year → £389K/year risk reduction, 162x ROI)

**Scalability Patterns:**

*Horizontal (Add More Instances):*
- Auto-scaling: 70% CPU → provision new instance

*Vertical (Bigger Machines):*
- Database: db.t3.medium → db.t3.large (more memory)

*Read Replicas:*
- Analytics queries hit replica (not primary)
- Primary stays available for application
- Spreads database load

**Evidence: PostgreSQL Schema Design**

```sql
-- PostgreSQL: Companies Table (validation layer)
CREATE TABLE companies_house.companies (
    company_id SERIAL PRIMARY KEY,
    company_number VARCHAR(8) NOT NULL UNIQUE,
    company_name VARCHAR(255) NOT NULL,
    incorporation_date DATE NOT NULL,
    dissolution_date DATE,
    company_status VARCHAR(50) NOT NULL,
    sic_code_1 VARCHAR(5),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT check_valid_dates CHECK (incorporation_date <= CURRENT_DATE),
    CONSTRAINT check_dissolution_after_incorporation 
      CHECK (dissolution_date IS NULL OR dissolution_date >= incorporation_date),
    INDEX idx_company_number (company_number),
    INDEX idx_incorporation_date (incorporation_date)
);

-- Validation Stored Procedure
CREATE FUNCTION validate_company_record(
    p_incorporation_date DATE,
    p_dissolution_date DATE
) RETURNS BOOLEAN AS $$
BEGIN
    IF p_incorporation_date > CURRENT_DATE THEN
        RETURN FALSE; -- Reject future dates
    END IF;
    IF p_dissolution_date IS NOT NULL 
       AND p_dissolution_date < p_incorporation_date THEN
        RETURN FALSE; -- Reject invalid dissolution dates
    END IF;
    RETURN TRUE;
END;
$$ LANGUAGE plpgsql;
```

### K13: Requirements Analysis & Specification

**Mapped to:** Project 2 (K12 Data Platform) - Requirements gathering & specification

**Definitional Understanding:** Requirements analysis encompasses **business discovery** (understanding stakeholder needs), **technical translation** (converting business needs into specifications), **scope management** (handling trade-offs), **change management** (adapting when requirements evolve), and **acceptance criteria** (how we test that requirements were met).

**Framework: "Understand Before Building"**

I follow a 4-phase approach to avoid building the wrong thing:

```
Phase 1: DISCOVER
- Who are the users/stakeholders? (business context)
- What problem are we solving? (current state pain)
- What success looks like? (measurable targets)
- What are constraints? (budget, timeline, compliance)

Phase 2: ANALYZE
- Break down requirements into components (functional + non-functional)
- Identify dependencies and conflicts
- Spot ambiguities early via clarifying questions
- Map dependencies and risk areas

Phase 3: DOCUMENT
- Write functional specifications (what system does)
- Write non-functional specifications (how system behaves: performance, cost, security, scalability)
- Create acceptance criteria (how we test each requirement)
- Align with stakeholders and get sign-off

Phase 4: VALIDATE
- Does technical design match requirements?
- Can we test against acceptance criteria?
- Are we ready to build?
```

### S11: Determine and Use Appropriate Data Analysis Techniques

**Mapped to:** Project 2 (K12 Data Platform) - Data quality analysis and predictive modeling

**Definitional Understanding:** Data analysis techniques encompass **descriptive** (what happened?), **diagnostic** (why did it happen?), **predictive** (what will happen?), and **prescriptive** (what should we do?). Each technique requires different data, skills, and validation approaches.

**Technique Selection Framework:**

```
Business Question
├─ "What happened?" (describe the past) → DESCRIPTIVE ANALYSIS
│  ├─ SQL aggregations (sum, count, avg, stddev)
│  ├─ Distributions (percentiles, quartiles)
│  └─ Comparisons (before/after, by category)
│
├─ "Why did it happen?" (understand causes) → DIAGNOSTIC ANALYSIS
│  ├─ Correlations (what moves together)
│  ├─ Fuzzy matching (duplicates, near-matches)
│  ├─ Cohort analysis (group comparisons)
│  └─ Root cause analysis (drill-down)
│
├─ "What will happen?" (predict future) → PREDICTIVE ANALYSIS
│  ├─ Regression (continuous values)
│  ├─ Classification (categories: yes/no, high/medium/low)
│  ├─ Anomaly detection (outliers, fraud)
│  └─ Time series (trends, seasonality)
│
└─ "What should we do?" (prescribe action) → PRESCRIPTIVE ANALYSIS
   ├─ Optimization (best path)
   ├─ Simulation (what-if scenarios)
   └─ Recommendations (personalized actions)
```

## Project 7: Pricing Service Quality Refactoring

### Business Context
You have a piece of code that calculates prices. It works, but it's hard to test, hard to change, and if one part breaks, the whole thing breaks. We separated it into layers: pricing rules separate from storage, calculations separate from HTTP, time separate from business logic. Now you can test each part alone, fix one thing without breaking others.

### Technical Implementation

**Problem Identified (7 Quality Gaps):**
1. HTTP handling + business logic tangled (monolithic)
2. Direct file I/O (can't run tests without real files)
3. Pricing rules embedded in conditionals (invisible rules)
4. Non-deterministic time (DateTime.now() makes tests unrepeatable)
5. Multi-stage rounding (accuracy issues)
6. Weak input validation (garbage in, garbage out)
7. Magic numbers (5%, 10%—where do these come from?)

**Architecture Redesigned (Layered):**
```
HTTP Layer (FastAPI)
  ↓
Service Layer (orchestration, business rules)
  ↓
Strategy Components (specific rules: PlanPricer, VolumeDiscountStrategy, TaxCalculator)
  ↓
Repository Layer (persistence abstraction)
```

**Design Patterns Applied:**
- **Service Layer**: Decouples business logic from HTTP → testable without web requests
- **Repository**: Abstracts persistence (file → in-memory → database)
- **Strategy**: Explicit pricing rules (not buried in if/else)
- **Clock Injection**: SystemClock (production) vs FixedClock (tests)
- **Dependency Injection**: Components receive dependencies (testable, composable)

**Test Portfolio (90 tests):**
- 34 characterisation tests (capture v0 baseline, detect regressions)
- 23 unit tests (pricing rules 10, repositories 10, clock 3)
- 19 service tests (orchestration verification)
- 14 integration tests (API boundary, complete flow)

**Results:**
- Line coverage: 99%
- Branch coverage: 92%
- Execution time: 0.21 seconds
- Defects caught: 7 quality gaps resolved

**Honest Gaps Acknowledged:**
- Gap 5 (rounding fragmentation): Partially addressed, requires further Strategy refinement
- Concurrency: Invoice write locking untested (file-based system limitation)
- Production concerns: Logging, monitoring, resilience designed but not implemented
