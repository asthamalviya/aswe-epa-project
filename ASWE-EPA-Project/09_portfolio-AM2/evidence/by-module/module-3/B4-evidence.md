## Action

### 1. How I approach learning
I learn through a cycle: doing a piece of work, reflecting on what went well and badly, drawing a general lesson from it, and applying that lesson to the next piece of work (Kolb, 1984). My portfolio shows this cycle across projects:

| Where I learned it | What I learned | Where I applied it next |
|---|---|---|
| Module 3: network security review | How segmentation limits the spread of an attack (WannaCry, EternalBlue) | Module 6: scoping IAM to one bucket and three actions to limit the reach of a compromised instance |
| Module 4: cloud ETL | Automation alone is not enough: transformations must be auditable, reproducible and compliant; real data needs probabilistic matching, not just exact rules | Module 6: governance logging built in from the start |
| Module 4: running PySpark locally | Local environment differences cause failures, which is why teams standardise environments | Module 6: containerising with Docker to pin the Python version |
| Module 6: three CI failures | Treat environmental assumptions (Python version, credentials, network configuration) as things to validate, not constants | [EVIDENCE NEEDED: a later project where you applied this] |
